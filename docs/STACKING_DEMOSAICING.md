# Bayer demosaicing follow-up

This follows the initial stacking/calibration record in `STACKING_CALIBRATION.md`.
The algorithm selection is part of the scientific decoding path, before stacking,
not a filter applied to the displayed PNG.

## User workflow

For Bayer input, live and offline stacking show one compact **Bayer demosaic**
selector. Its menu contains **DDFAPD (recommended)**, **VNG**, and **Bilinear (fast)**.
New stacking workspaces default to DDFAPD. Mono and already-interleaved RGB input
bypass demosaicing and do not show the selector. Live visibility follows the actual
raw camera callback format, not just the camera's requested preview format.
If the selected algorithm exceeds the processing budget, the source and selector
remain available so the user can choose a lower-memory method and retry.

Changing a completed/analyzed offline workspace asks the user to save first,
invalidates its analysis/result, reloads the first frame, and requires analysis
again. A running or paused live stack must be reset before the algorithm can
change. The algorithm is fixed in the session key and offline analysis context,
so one stack cannot silently combine frames processed by different algorithms.
Re-decoding the same file preserves the chosen crop rectangle.

## Algorithms and precision

- **DDFAPD:** Menon (2007), including directional green estimates, a posteriori
  direction selection, color-difference reconstruction and all three refinement
  stages. The port follows the [Colour 0.2.7 implementation](https://github.com/colour-science/colour-demosaicing/blob/8e01cc06f111eda944ff8955bc9579e894ff142a/colour_demosaicing/bayer/demosaicing/menon2007.py).
- **VNG:** variable-number-of-gradients reconstruction based on OpenCV's scalar
  VNG implementation, adapted to floating-point linear sensor values. Its eight
  directions use a local gradient threshold and color differences. A two-pixel
  border uses bilinear interpolation; very small images consist entirely of that
  border. The reference and adaptation details ship in
  `app/src/main/assets/THIRD_PARTY_OPENCV_VNG.txt`.
- **Bilinear:** the existing floating-point interpolation path, retained as an
  explicit option and as the default for legacy low-level reader calls.

The order is **decode sensor samples → optional BIAS/DARK/FLAT → selected
demosaicing → software binning → registration/stacking → display processing**.
No method first reduces data to an 8-bit display image. All four Bayer patterns
and the actual ROI parity are handled. Negative and above-white calibrated values
are retained. Original SER/PSER recordings and their calibration capture settings
are unaffected by a change to this downstream algorithm.

Saved FITS metadata and JSON include `demosaicAlgorithm` and demosaicing scratch
memory. Non-Bayer products record `NONE`. Existing exports are not relabeled or
retroactively reconstructed. White balance and ordinary camera/player previews
retain their existing behavior.

## Resource limits

DDFAPD uses four reusable Double planes and one Byte direction plane, reserving
`33 * sensorPixels + 4096` bytes beyond the sensor input and output RGB. VNG uses
bounded row buffers (`168 * width + 4096` bytes, or 4096 for a border-only image).
The coordinator includes the selected algorithm's extra
memory at full sensor resolution before admitting live/offline processing,
including when software binning reduces the eventual stack dimensions. Row-level
cancellation prevents a cancelled offline operation from finishing an entire
large demosaic first. No native OpenCV or Python runtime is added to the APK.

Directional demosaicing can reduce artifacts on some edges and textures; no
method guarantees removal of grid patterns, false colors or undersampling
artifacts on arbitrary sky data. CPU time, memory pressure and real-camera image
quality still need physical-device/real-sky verification.

## Verification

The independent DDFAPD fixture is generated by `scripts/generate_demosaic_reference.py`
using separately installed Colour 0.2.7. Its 16 cases cover four CFA patterns,
odd/even/small dimensions, borders and Float32 inputs outside [0, 1]. The checked-in
golden output is compared against every output sample with a 2e-6 tolerance.
Across 2,484 output samples, the observed maximum absolute difference was
1.22e-7 (RMS 2.40e-8).

`scripts/verify_vng_reference.py` independently regenerates a four-CFA oracle with
`opencv-python-headless==4.10.0.84`. The pinned OpenCV scalar implementation returns
interior samples displaced by two rows, verified using the unchanged native CFA
channel of an asymmetric input. This port preserves original sensor coordinates;
the reference comparison explicitly aligns those coordinates and excludes borders.
All 8,700 compared channel values differed by at most 0.400 DN, below the 0.501 DN
rounding tolerance. Unlike the 8-bit reference, the application retains fractional,
negative and above-white values. The script and fixture metadata document these
adaptations rather than claiming bit-identical OpenCV output.

Synthetic quality checks (not real-sky acceptance):

| Scene | Bilinear RGB RMSE | Directional RGB RMSE |
| --- | ---: | ---: |
| Axis-aligned color edge, DDFAPD | 0.03595 | 0.01574 |
| 45-degree gray edge, VNG | 0.049217 | 0.045870 |
| Diagonal gray sinusoid, VNG | 0.013638 | 0.009044 |
| Gray sine/cosine texture, VNG | 0.007765 | 0.005003 |

The VNG scenes use 65x63 RGGB samples and exclude a three-pixel border. On the
diagonal sinusoid, mean absolute R-minus-B error fell from 0.011196 to 0.001887.
JUnit also checks these gray scenes across all four CFA phases. These particular
scenes demonstrate reduced interpolation error; they do not establish a universal
ranking on noisy or undersampled astronomical data.

A desktop JDK 17 microbenchmark at 1024x768 (four warmups, median of five runs)
measured 14.79 ms bilinear, 41.33 ms VNG and 35.33 ms DDFAPD. These are desktop
measurements, not Android frame-rate or thermal claims.
Reference scripts and tests are development-only dependencies.

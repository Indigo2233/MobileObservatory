# 相机可见光色彩与 SER CFA 选择

2026-10-14。来自 AE676C（3536×3536）两张色卡截图的回归修复；与 [WF 第零批/第一批](WF_PHASE_0_1_ACCEPTANCE.md) 同批交付。截图不能单独证明硬件 ADC 位深或正确的 CFA 排列，修复依据是代码中的明确错误和合成原始样本的数值验证。

## 1. 色彩错误与修复边界

| 问题 | 修复 |
|---|---|
| `FrameProcessor` 和 `SERReader` 默认开启 LP700 红外转换；其矩阵会交换/组合可见光通道并产生负值裁切 | 正常预览/播放默认关闭；显式红外转换仍保留。没有根据色卡外观盲目交换 RGGB/BGGR |
| 大尺寸 Bayer 预览用偶数步长直接取 `x*step,y*step`，所有输出点落在相同 CFA 位置，之后又当作完整 Bayer 解色 | 显示降采样选择完整 2×2 CFA 单元，保留四个相位；3536² 输入缩到 1768² 时橙/蓝通道仍分别正确 |
| 软件 bin 把不同 CFA 颜色混合后仍标成 Bayer | 同相位分别平均，保留排列和有效尺寸，覆盖 bin 2/3/4 与不整除边缘 |
| 低照度数据仅凭数值猜位深可能被当成更高位数，左右对齐/字节序也可能影响亮度 | 已知 SDK 的 `PixelTraits` 随预览入队快照，优先按有效位数、对齐、字节序解释；未知布局才沿用检测 |
| 白平衡在显示拉伸/裁切之后应用，单次 AWB 下一帧才生效 | 在线性传感器样本上计算并于同帧应用，再做显示映射 |
| MP4 转换器把 RGB24/RGB48 落到单色分支，并忽略已知高位布局 | 正确读取 RGB/BGR、高位左右对齐和字节序；开录固定布局，不在写线程追读变化的相机配置 |

正常相机 JPG、预览与 MP4 使用明确的布局；单张拍摄在等待帧之前固定目标名称，浏览新目标不会给尚未完成的旧拍摄换名。SDK 二进制没有变化，原始 SER/FITS 录制入口与科学标定/叠加不套用显示矩阵或显示降采样。

FITS 图像查看器在 LP700 开关右侧提供说明入口。说明对话框交代适用滤镜、显示处理阶段、数据边界与默认关闭建议，并注明算法作者与来源；关闭后保留当前文件和 LP700 开关状态。

### LP700 银心偏红：待实图复现（2026-10-15）

用户反馈手机预览中的银心主体偏红，与电脑效果不同。当前缺少同一原始 FITS、电脑端处理公式/参数及结果截图，尚未复现该色差；本次保持矩阵系数、白平衡与显示处理参数，不能将署名修正计为色彩问题已修复。

已核对的处理入口：

- 整数/外部 FITS：按百分位选显示窗口；Bayer 路径先转 8 位并去马赛克，再应用 LP700 矩阵及整图白平衡；RGB 路径使用显示窗口归一化值做矩阵变换。之后应用 8 位背景校正和显示曲线。
- 本应用导出的归一化 Float32 FITS：在线性浮点图上应用 LP700 矩阵及整图白平衡，再恢复保存的显示配方。该路径与整数 FITS 的量化、窗口和后处理阶段存在差异。
- 实时相机及 SER 的显式 LP700 路径：使用已映射的预览像素，附加整图白平衡和背景校正；原始科学数据保留。

对照验收需要同一文件、相同 CFA 和去马赛克方式，以及电脑端 LP700 公式/白平衡/拉伸设置。比较线性 RGB、矩阵输出、白平衡后及最终显示四个阶段，保留负值与高光裁切记录，确认差异来源后补实际调用路径的数值回归。2026-10-15 已从 vivo 取得用户当前查看的 `pp_0000.fits` 原文件并确认手机页面开启 LP700；电脑端参考结果及阶段参数仍缺失，PixInsight 只读连接超时，尚未完成色彩对照。

## 2. 手动 CFA 的入口和语义

**影像 → 录像 → 后处理 → 颜色排列（CFA）**，也可先进入“导入录像”。默认“自动”读取文件声明；可选择单色、RGGB、BGGR、GRBG、GBRG。软件本来就能读取单色 SER，新增的是缺失/错误 CFA 标记时的显式解释覆盖。

- 单色保持一个样本通道，不做去马赛克；Bayer 继续提供 DDFAPD、VNG、双线性。
- CFA 描述文件输出像素网格，不再额外套用拍摄 ROI 偏移。已经是 RGB/BGR 三通道的文件不会被当作原始 CFA。
- 不改写用户原文件或头字段；外部文件仍沿用应用已有导入副本流程。未知但有效的单样本标记允许保留副本、选排列后重读，负值/非法容器仍拒绝。
- 修改排列会重读预览并失效原质量分析/叠加结果；已有分析或结果时给更改/取消选择。文件身份与解码身份分开，避免旧分析套到新排列。
- FITS/JSON 导出记录原头 `colorId`、选择模式、实际传感器排列、位序和去马赛克算法；可复查结果来源。
- 新建校准主帧有独立 CFA 选择。主帧的有效排列固定，与光帧不兼容时拒绝应用；不把光帧覆盖值暗中套给所有校准场。BIAS/DARK/FLAT 仍全部可缺省。

## 3. 验证与仍需实测

### MP4 和大尺寸叠加启动修复（2026-10-17）

- MP4 编码输入先读取 ByteBuffer 容量，再取得并填写 Image；取得 Image 后不再调用同索引的 `getInputBuffer`，避免图像失效。无 Image 时重新取得 ByteBuffer。依据 [Android MediaCodec 输入缓冲契约](https://developer.android.com/reference/android/media/MediaCodec#getInputBuffer(int))。
- 按每个 Y/U/V 平面的实际 position、rowStride、pixelStride 写入，兼容 UV/VU 共享存储，不靠各自 ByteBuffer 的相对位置猜色度顺序。截断缓冲、写入、EOS 排空和 muxer 收尾异常向录制会话传播；空视频不记成功。编码尺寸选择同时核对帧率。MP4 可录制 RGB/Live View 显示帧；SER/PSER/FITS 的科学来源限制保持，测试模拟相机仍只演示、不保存。
- `CalibrationGeometry` 只校验元数据有效性，不能在读取大 SER 头或未启用校准场时提前抛出 `calibration_dimensions`。主帧构建/加载、实时和后期处理入口继续在分配像素前检查尺寸和内存预算；该次修复保留了 419 万像素上限及实际算法预算；2026-10-18 后统一 4 MP 门槛已由工作集预算取代，见 `STACKING_CALIBRATION.md` 的 Adaptive ROI planning。
- 实时叠加的开始按钮与实际启动复用尺寸/内存预检。超限标红；无选中校准场且未录制时，按相机声明的硬件合并倍率、完整传感器尺寸和当前算法预算推荐“全幅 N× 像素合并”。用户点击才更改采集设置，随后等待新帧再启动；不自动裁切、忽略校准场或拿显示端软件合并绕过原始帧预算。后期大 SER 保留文件信息与 CFA/算法选项，并明确提示降低采集分辨率。
- 验证覆盖实际 MediaCodec/MediaMuxer 写入、MP4 解码色度/时长、3536² Bayer 视频、空录像失败、大图读取/启动预检和既有 BIAS/DARK/FLAT 流程。模拟器通过不代替 S23 Ultra 的实际编码器及相机硬件合并验收。

2026-10-17 收到的现场日志补充：Player One **Uranus-C PRO** 实际输出 3856×2180（8,406,080 像素），先 RAW8、后 RAW16；该会话运行 build 47，尚无修复版 build 48 记录。全幅超过现有处理像素上限；2× 后约 210 万像素也可能超过算法内存预算，不能只按像素数宣告可叠加。推荐倍率继续由 SDK 实际能力和内存预算决定，未声明支持的倍率不显示。现场链路明确为 `HIGH_SPEED` / `usb3=false`，RAW8 约 4.9 fps、RAW16 约 2.4 fps，与 USB 2.0 传输瓶颈一致；这不是 MP4 失败的独立证据。

原 `app.log` 没有 MP4、叠加失败堆栈：这些路径只写 Android Logcat。已补入可导出的文件日志，包括录制请求/阻断状态、候选编码器配置失败、实际编码尺寸、首帧平面布局、写入/收尾失败、叠加请求尺寸/预算/失败原因、Player One 的 SDK 合并倍率及实际合并结果。首帧布局只记录一次，避免逐帧磁盘日志；时间戳格式化与文件写入串行化。日志缺失不能证明现场没有点击录制，也不能据此确认具体编码器错误。新增 3856×2180 RAW16 编码回读及 585 尺寸预算回归；不提交用户的原始日志或设备序列号。

实际尺寸回归还发现编码器多次降尺寸时，反复对已对齐尺寸缩放会积累宽高比误差；改为始终从原始传感器宽高计算每级缩放，再执行 16 像素对齐。例如只支持 1920×1080 范围的编码器由 3856×2180 选取 1632×928，而非比例偏差更大的 1632×944。

Player One 当前 Auto 布局声明来自传感器 CFA，尚未声明偶数硬件合并后的输出 CFA 已验证；不能因 4× 尺寸较小就强行放行彩色叠加或假定每台设备支持该倍率。该路径无可验证合并建议时，可先保持 Bin 1、使用较小采集 ROI 验证叠加；1024×576 的 Bayer DDFAPD 预检在 128 MiB 科学预算内通过。它是缩小视野的诊断配置，不代表全幅 585C 彩色叠加已完成适配。

### 录像收尾与 ROI 应用反馈（2026-10-19）

停止录像立即停止接收新帧，已有队列和文件关闭继续由原写线程完成。拍摄底栏显示“正在完成录像”，期间禁用再次开录，文件忙碌状态持续到收尾和来源侧车更新结束。界面不再用 3 秒阻塞等待对编码器的正常排空作失败判定；真实编码、写盘、关闭失败继续传播。相机设置任务通过可取消的挂起等待观察完成，取消等待者不会中断写线程或改变录像结果。底层显式限时等待仍供需要强制判失败的诊断/测试调用使用。

ROI、Bin、像素格式和读出模式等布局变化先结束包括 MP4 在内的旧录像，后台等待旧文件完成后再写 SDK。由此避免旧 `sampleTraits` 解释新位深：最小复现中，按 RAW8 开录配置解读左对齐 RAW12 时亮度为 235，正确配置为 71。每段录像继续使用开录时固定的布局。

拍摄与叠加共用 ROI 应用状态：请求受理后显示应用中，SDK 写入、ROI 读回和采集重启完成后显示成功；设备拒绝、读回不符或配置变化显示失败及重试说明。应用前在后台事务内再次核对布局、录制/拍照、叠加和校准状态；失败时保留相机实际读回的 ROI，关闭面板不取消已提交的设备写入，重新打开可见最终结果。

回归覆盖写线程挂起等待/取消、界面停止期间的后台关闭、旧录像结束后才接受像素格式、ROI 读回失败及重试、弹窗进度与成功/失败状态。当前本地连接的是 32 位 Samsung J7，不能执行 arm64 应用的 Android instrumentation；真实编码器和实际相机仍需在兼容设备上运行对应回归。
